## 계층형 기억 시스템 상세

## 계층형 기억 시스템 (파일 구조)

> **채팅은 잊지만, 파일은 잊지 않는다.**

```
프로젝트 루트/
├── GEMINI.md             ★ 프로젝트 신분증 (모든 세션이 최초 읽음)
├── DECISION_LOG.md       ★ 장기 결정 로그 + 문서 우선순위 (중요 결정 보관)
├── PROJECT_TASKS.md      ★ 전체 진행 조감도 (Phase별 태스크 현황)
├── PRD_v1.0.md           (기획 — 전략 모드에서만 읽음)
├── DESIGN_SYSTEM.md      (디자인 — 전략 모드에서만 읽음)
├── PROJECT_BRIEF.md      (오피스아워 결과)
├── _context.md           ★ 현재 상태 (항상 30줄 이내!)
├── _order.md             현재 단건 작업 지시서 슬롯 (덮어쓰기)
├── _playbook.md          현재 배치 플레이북 슬롯 (덮어쓰기)
└── _archive.md / docs/history/  압축된 과거 기록 (평소 안 읽음)
```

### _context.md (핵심! 항상 30줄 이내)

이 파일이 **프로젝트의 실질적 두뇌**다. 총괄은 매 세션 시작 시 이것만 읽으면 현재 상태를 즉시 파악할 수 있다.

> 📁 **템플릿:** `skills/총괄매니저/templates/context_template.md`

**롤링 규칙** (큐처럼 작동):
- "최근 완료" **최대 5건** — 초과 시 → `_archive.md`로 이동
- "핵심 결정" **최대 5개** — 초과 시 → `_archive.md`로
- "다음 할 일" **2~3개만** — 먼 미래까지 적지 않음
- **총 30줄 이내 유지 불변** (서식상 1~2줄 초과 허용)

### _archive.md / docs/history/ — 장기 보관, 평소 안 읽음. 완료 작업/과거 결정을 압축 보관.
### _order.md — 현재 작업 지시서 1건을 담는 슬롯. 작업자가 읽고 실행하고 결과 기록.
### _playbook.md — 현재 배치 플레이북 1건을 담는 슬롯.

### 오더/플레이북 슬롯 규칙
- 루트에는 `_order.md`와 `_playbook.md`만 둔다.
- 새 오더/플레이북을 발행할 때 기존 완료본이 있으면 먼저 archive로 이동하거나 요약 보관한다.
- `_order_028.md`, `_playbook_round2.md` 같은 루트 변형 파일을 만들지 않는다.
- 위험 분리건도 별도 루트 파일을 만들지 말고, 현재 작업이 끝난 뒤 `_order.md`를 다음 위험 오더로 덮어쓴다.
### DECISION_LOG.md — 장기 결정 로그. KPI, 저장 규칙, 아키텍처, 금지사항, 피벗처럼 프로젝트 방향에 영향을 주는 결정은 반드시 기록한다.

### 운영 로그 우선 원칙

대시보드는 멋있지만 초반 운영 안정성은 로그가 만든다. 성과 추적 기능을 만들 때는 대시보드보다 아래 로그 파일을 먼저 설계한다.

| 로그 | 역할 |
|------|------|
| `performance_log.md` | 콘텐츠별 성과 수치 기록 |
| `content_calendar.md` | 발행 계획과 실제 발행 이력 |
| `experiment_log.md` | 이번 주 실험 가설, 결과, 다음 액션 |

**원칙:** 데이터가 2~4주 쌓이기 전까지는 대시보드를 만들지 않는다. 먼저 로그가 일관되게 채워지는지 확인한다.

### 스킬 최소 출력 기준 원칙

스킬이 길어질수록 품질이 흔들린다. 모든 중요한 `SKILL.md`는 끝부분에 "최소 출력 기준"을 가져야 한다.

```
## 최소 출력 기준
이 스킬이 성공한 것으로 보려면 최소한 아래 산출물이 나와야 한다.
- [필수 산출물 1]
- [필수 산출물 2]
- [검수 또는 채점 기준]
```

예:
- 블로그엔진: 제목 후보, 본문, 해시태그, 내부링크, 품질 채점
- 인스타엔진: 목적 태그, 파일 구조, CTA, DM 가이드, 성과 입력
- 총괄매니저: 상태 브리핑, 기록 업데이트, 오더/플레이북, 결정 로그

### 스킬/레퍼런스 분리 원칙

스킬이 비대해지면 아래처럼 분리한다.

| 파일 | 역할 |
|------|------|
| `SKILL.md` | 실행 절차, 판단 흐름, 필수 규칙 |
| `REFERENCES.md` | 예시, 템플릿, 샘플 문구, 레퍼런스 |
| `CHECKLIST.md` | 검수표, 완료 기준, Hard Fail |

**판단 기준:** `SKILL.md`가 400줄을 넘거나 예시가 절반 이상을 차지하면 `REFERENCES.md`와 `CHECKLIST.md`로 분리하는 것을 검토한다.

### 문서 우선순위 (Source of Truth)

문서 간 충돌이 생기면 아래 순서로 판단한다. 새 프로젝트의 `GEMINI.md`에도 이 우선순위를 기록한다.

1. `AGENTS.md` 또는 프로젝트 전용 에이전트 지침 — 프로젝트 헌법
2. `DECISION_LOG.md` — 장기 결정과 변경 이유
3. `PRD_*.md` — 제품·기능 요구사항
4. 운영/브랜드/디자인 문서 — `BRAND_CONTEXT.md`, `DESIGN_SYSTEM.md`, 운영 가이드 등
5. 외부 또는 전역 `SKILL.md` — 실행 방법론
6. `_order.md`, `_playbook.md` — 현재 작업 지시
7. 채팅 내용 — 즉시 맥락. 장기 결정은 반드시 파일로 승격

## 작업 분해 상세

## 작업 분해

큰 작업을 받으면 Step별로 분해한다.

### 분해 규칙
1. **한 Step = 한 오더 (단건)** 또는 **한 Phase = 한 플레이북 (배치)**
2. **의존성 표시 필수** — `[독립]` vs `[의존: Step N 후]`
3. **각 Step에 난이도·모델·시간 배정**
4. **파일 충돌 금지** — 같은 파일을 건드리는 Step은 반드시 순차 또는 하나로 합침

### 플레이북 그룹핑 규칙 ⭐

분해된 Step을 플레이북에 묶을 때:
- **독립 Step끼리** → 하나의 플레이북에 순서대로 묶음 (작업자 1세션)
- **위험 Step** (아키텍처 변경, 신규 패턴) → 다음 `_order.md` 슬롯으로 분리
- **파일 충돌 Step** → 반드시 순서 지정 (플레이북 내 순서로 해결)

### 분해 출력 포맷
```
📋 작업 분해 — "[작업명]"

Step 1: [작업명] 🟢 쉬움 | [독립]     | ⏱️ ~10분
Step 2: [작업명] 🟡 보통 | [독립]     | ⏱️ ~20분
Step 3: [작업명] 🟡 보통 | [의존: 1,2] | ⏱️ ~15분
Step 4: [작업명] 🔴 위험 | [독립]     | ⏱️ ~30분 ← 분리 추천

📦 플레이북: Step 1→2→3 (1세션)
📋 분리 오더: Step 4 (현재 플레이북 완료 후 `_order.md`를 덮어써 별도 세션)
총 예상: ~1시간15분

플레이북을 생성할까요?
```

## 오더 생성 상세

## 오더 생성

### 토큰 효율 원칙 ⭐ (v2.6 강화)

> ⚠️ **총괄은 코드를 작성하지 않는다. 방향을 작성한다.**
> 오더에 전체 컴포넌트 코드를 넣으면 총괄이 코드를 생성하고, 작업자가 또 생성하여 **토큰이 이중으로 소모**된다.
> 작업자 AI는 주변 파일을 직접 읽고 패턴을 파악하는 능력이 있다. 이것을 활용한다.

**📏 오더 길이 상한:**
- 🟡 보통 오더 (텍스트 프롬프트): **30줄 이내**
- 🔴 복잡 오더 (_order.md): **150줄 이내** (작업 결과 섹션 제외)
- 이 상한을 넘기면 오더를 분할하거나, 코드를 삭제한다.

```
오더에 넣어야 할 것:
✅ 뭘 만들지 (목표, 결과물)
✅ 어떤 파일/패턴을 참조할지 ("ColorCard.tsx 패턴 따라서")
✅ 인터페이스/Props 정의 (타입은 정확해야 하므로)
✅ 핵심 주의사항 (params Promise 등 실수하기 쉬운 것)
✅ 금지사항 (건드리면 안 되는 것)
✅ 완료 기준

오더에 넣지 말아야 할 것:
❌ 전체 컴포넌트 코드 (작업자가 직접 작성)
❌ 전체 CSS 코드 (디자인 토큰 참조 지시만)
❌ JSX 렌더링 구조 (작업자가 설계)
❌ 줄 번호별 상세 변경 지시 (단순 수정 제외)
```

### 코드 포함 기준 (예외 — 엄격 적용)

| 상황 | 코드 포함 | 이유 |
|------|----------|------|
| 기존 패턴 따라가는 신규 | ❌ "ColorCard 참조해서 만들어" | 참조 대상 지정이면 충분 |
| 패턴이 명확한 수정 | ❌ 한 줄 지시만 | 작업자가 파악 가능 |
| 위험한 API (params Promise 등) | ✅ **해당 1~3줄만** | 실수 방지 |
| 인터페이스/타입 정의 | ✅ **Props 타입만** | 타입 불일치 방지 |
| 프로젝트에 참조 파일이 하나도 없는 완전 신규 패턴 | ✅ **최소 골격만** (~20줄) | 참조 대상 없음 |

> ⚠️ "참조 파일이 있다면 코드를 넣지 않는다"가 기본 원칙이다.

### 오더 작성 후 셀프체크 (필수)

오더 초안 완성 후, 코드블록마다 아래를 자문한다:
```
"작업자가 참조 파일을 읽으면 이 코드 없이도 만들 수 있는가?"
→ Yes면 삭제하고 참조 경로만 남긴다.
→ No면 유지하되 핵심 스니펫으로 축소한다.
```

프롬프트 오버헤드가 더 큰 경우 직접 수정하고 _context.md에 기록.

### 🔴 복잡 → _order.md 파일 저장

> 📁 **템플릿:** `skills/총괄매니저/templates/order_template.md`를 읽고 값을 채워 저장한다.
> 💡 **코드는 최소한으로.** 인터페이스 정의 + 참조 파일 경로 + 핵심 스니펫만 포함.
> 🔁 **슬롯 규칙:** 기존 `_order.md`가 완료본이면 archive로 이동한 뒤 같은 파일을 덮어쓴다.

저장 후: `📋 작업지시서 #NNN 저장 완료! 📁 [루트]/_order.md | 🤖 [모델명]`
→ 사용자에게 안내: *"새 채팅방에서 '_order.md 읽고 실행해줘'라고 말하세요"*

### 🟠 배치 → _playbook.md 생성 ⭐ (v2.7 신규)

> 📁 **템플릿:** `skills/총괄매니저/templates/playbook_template.md`를 읽고 값을 채워 저장한다.
> 💡 **하나의 플레이북 = 하나의 작업자 세션.** 작업자가 순서대로 전부 실행.
> 🔁 **슬롯 규칙:** 기존 `_playbook.md`가 완료본이면 archive로 이동한 뒤 같은 파일을 덮어쓴다.

**플레이북 구성 원칙:**
1. Phase 내 **일반 작업**을 순서대로 묶는다 (보통 3~5개 Task)
2. 각 Task에 **체크포인트** 명시 (빌드/린트 통과 확인)
3. 각 Task에 **판단 가이드** 포함 (애매한 상황의 대처 기준)
4. 마지막에 **기록 위임 섹션** 포함 (작업자가 _context.md, PROJECT_TASKS.md 업데이트)
5. **위험 작업**은 플레이북에 넣지 않고 다음 `_order.md` 슬롯으로 분리

**위험 작업 판별 기준:**
- 아키텍처 변경, 신규 패턴 도입
- 4개+ 파일 동시 수정
- 실패 시 다른 Task에 연쇄 영향
→ 해당하면 분리. 아니면 플레이북에 포함.

**플레이북 길이 상한:** Task 당 30줄 이내 × 최대 5 Task = **150줄 이내** (기록 위임 섹션 제외)

저장 후: `📦 플레이북 Phase N 저장 완료! 📁 [루트]/_playbook.md | 🤖 [모델명]`
→ 사용자에게 안내: *"새 채팅방에서 '_playbook.md 읽고 순서대로 실행해줘'라고 말하세요"*
→ 위험 분리건 있으면: *"플레이북 완료 후 다음 세션에서 '_order.md'를 위험 오더로 덮어써 별도 실행합니다"*

### 🧹 위생 정리 오더 (Sanitation Order) (🔴 복잡형)

암행어사의 [위생 점검 리스트]를 조치하기 위해 발행하는 오더이며, 코드와 문서의 싱크를 맞추거나 쓰지 않는 레거시 코드를 안전하게 삭제하도록 Coder에게 지시합니다.

```
🧹 [위생 정리 오더] 레거시 정리 및 동기화 작업

1. 대상 및 목표
- 암행어사 진단 파일: [_audit_YYYY-MM-DD.md 경로]
- 정리 목표: [예: 안 쓰는 OldCard.tsx 삭제 및 디자인 토큰 위반 hex 컬러 수정]

2. Coder 필수 수행 지침 (안전한 정리 프로토콜)
- [ ] **참조 제거 선행:** 코드를 지우기 전에 `grep_search` 등을 사용하여 프로젝트 전체에서 해당 파일이나 변수 임포트가 완전히 제거되었는지 더블 체크하십시오.
- [ ] **디자인 토큰 수렴:** 하드코딩된 스타일값을 지울 때 `DESIGN_SYSTEM.md`에 명시된 공식 변수명(`var(--color-primary)`)으로 치환하십시오.
- [ ] **문서 동기화:** 코드 리팩토링으로 사양이 변경되었다면 관련 `PRD_v1.0.md` 문서 등도 이에 맞춰 동시 업데이트하십시오.

3. 완료 기준
- 빌드 에러 및 타입 린트 에러가 없을 것.
- 삭제한 파일 목록과 의존성 제거 여부를 명확히 요약 보고서에 명시할 것.

🤖 모델: [추천] | 🏠 새 채팅방에서!
```

## 디버깅 오더 상세

## 디버깅 모드 (에러 대응)

에러의 난이도와 유형에 따라 디버깅 프로세스를 분기한다.

### 에러 난이도 분기 규칙
*   🟢 **단순 에러:** 단순 오타, 단순 린트 경고, 임포트 경로 누락 등.
    - 별도의 무거운 디버깅 오더를 작성하지 않고, 즉시 원인 분석 후 수정 오더를 텍스트 프롬프트(🟡보통형)로 하달한다.
*   🔴 **복잡 에러:** 알고리즘 결함, 런타임 크래시, 데이터 비일관성, 원인 불명의 빌드 에러 등.
    - 아래의 **4단계 디버깅 오더 양식**을 `_order.md` 파일에 기록하여 하달한다. Coder는 반드시 4단계를 밟고 분석 보고서를 작업 결과에 포함해야 한다.

### 복잡 에러 디버깅 오더 양식 (🔴 _order.md용)
```
🐛 [디버깅 오더] 근본 원인 규명 및 조치

1. 증상 및 재현 환경
- 에러 로그: [로그 또는 에러 메시지]
- 관련 파일: [관련 파일 경로]

2. Coder 필수 수행 지침 (디버깅 4단계 프로토콜)
Coder는 코드를 즉흥적으로 수정하지 말고 다음 단계를 준수하십시오.
- [ ] Step 1 (가설): 분석 결과를 토대로 에러 원인에 대한 1~2개 가설 수립
- [ ] Step 2 (격리): 의심 코드를 분리하거나 임시 검증 스크립트(scratch/ 등)로 에러 상황 재현
- [ ] Step 3 (수정): 가설에 입각한 최소한의 코드 수정 적용
- [ ] Step 4 (전파 방지): 프로젝트 전체에서 유사 패턴 검색 및 수평 조치

3. 완료 및 보고 기준
- 수정 내역과 함께 **[가설 ➔ 격리 ➔ 수정 ➔ 전파 방지] 각 단계의 수행 기록**을 작업 결과 보고서에 요약 보고하십시오.
- 빌드 및 린트 통과 여부를 명시하십시오.

🤖 모델: [추천] | 🏠 새 채팅방에서!
```

## 실패 복구 프로토콜 🚨

AI 작업 중 실패 시(컨텍스트 유실, 할루시네이션, 빌드 깨짐, 세션 끊김) 아래 절차를 따른다.

### 실패 유형별 대응

| 실패 유형 | 증상 | 복구 절차 |
|-----------|------|-----------|
| **세션 끊김** | 작업 중 채팅방이 닫힘 | 새 채팅방 → "총괄 시작" → _context.md의 "진행 중 작업" 확인 → 이어서 오더 |
| **빌드 깨짐** | 작업자가 빌드 에러 보고 | _order.md 결과 확인 → 에러 내용으로 수정 오더 생성 (최대 3회 시도) |
| **스코프 이탈** | 작업자가 지시 범위를 벗어남 | git diff 확인 → 범위 밖 변경 되돌리기 오더 → _context.md에 사고 기록 |
| **할루시네이션** | 없는 API/라이브러리 사용 | 해당 파일 원복 오더 → 올바른 방법 명시하여 재오더 |

### 체크포인트 규칙

- **오더 발행 전:** _context.md에 "진행 중: #NNN [작업명]" 기록
- **오더 완료 시:** "진행 중" → "최근 완료"로 이동
- **실패 시:** "진행 중: #NNN [작업명] ⚠️ 실패 — [사유]"로 업데이트

### 3회 실패 시 에스컬레이션

```
같은 작업이 3회 연속 실패하면:
1. 작업을 더 작은 단위로 분해
2. 실패 원인을 _context.md "핵심 결정"에 기록
3. 사장님에게 접근 방식 변경 제안
```

> 💡 **핵심:** 실패해도 _context.md만 있으면 어디서든 복구할 수 있다. 파일이 곧 백업이다.

### 캐스케이딩 업데이트 절차

```
PRD 변경 발생!
━━━━━━━━━━━━
Step 1. 변경 범위 판단
├── 🟢 소규모 (기능 1개 추가/삭제) → Step 2만
├── 🟡 중규모 (핵심 플로우 변경) → Step 2 + 3
└── 🔴 대규모 (타겟/방향 전환) → Step 2 + 3 + 4

Step 2. PRD 업데이트 → 변경 이력 섹션에 기록
Step 3. DECISION_LOG.md에 피벗 결정과 사유 기록
Step 4. 디자인시스템 영향도 체크 → 필요시 재생성 오더
Step 5. 기존 코드 영향도 체크 → 수정/삭제 오더 생성
```

### _context.md 기록
```markdown
## 핵심 결정

  영향: PRD v1.1 업데이트, 디자인시스템 토큰 유지, 코드 [파일명] 수정 필요
```

> 💡 소규모 변경이 대부분이다. 대규모 피벗은 드물지만, 절차가 없으면 문서와 코드가 따로 논다.

## 결과 평가 (코드리뷰)

### 트리거
- "결과 확인해" / "리뷰해줘"
- 작업자 결과 복사 붙여넣기 시
- "_order.md 결과 확인해" → 파일의 "작업 결과" 섹션 읽기

### 5대 체크

| 체크 | 항목 | 확인 |
|------|------|------|
| ✅/❌ | 스코프 준수 | 지시한 것만 했는가? |
| ✅/❌ | 금지 영역 보호 | 금지 파일/영역 건드리지 않았는가? |
| ✅/❌ | 디자인 토큰 | 하드코딩 없이 토큰 사용했는가? |
| ✅/❌ | 패턴 일관성 | 기존 패턴과 맞는가? |
| ✅/❌ | 완료 기준 충족 | 오더 기준 달성했는가? |

### 작업자 결과 상태 해석

코딩가이드 에스컬레이션 프로토콜에 따라 `_order.md`의 "작업 결과" 섹션은 아래 상태를 가질 수 있다.

| 상태 | 의미 | 총괄 행동 |
|------|------|----------|
| ✅ 완료 | 정상 완료 | 결과 검수 → 기록 업데이트 → 다음 오더 |
| ⚠️ 부분 완료 | 완료분은 있으나 나머지 진행 불가 | 완료분 검수 + 미완료분 새 오더 |
| 🟡 반려 | 오더 모호 또는 범위 초과 | 오더 재발행 또는 플레이북 변환 |
| 🔴 불가 | 완료 기준 달성 불가 | 대안 검토 → 새 오더 |

### 직접 코드 확인 의무 ⭐

> ⚠️ 작업자의 "완료 보고"만으로 채점하지 않는다.
> 반드시 최소 1개 핵심 파일을 직접 `view_file`로 열어 확인한다.

```
직접 확인 체크리스트:
[ ] 핵심 변경 파일 1개 이상 직접 열어 확인
[ ] 동적 라우트가 있는 경우 → params 처리 방식 확인
[ ] 새 import가 있는 경우 → 해당 모듈이 실제 존재하는지 확인
[ ] 채점 시 "직접 확인한 파일"을 기록
```

### 평가 등급
- **✅ 통과** (5/5): → **반드시 [2] 기록 업데이트 실행 후** 다음 작업
- **⚠️ 조건부** (4/5): 수정 프롬프트 생성
- **❌ 반려** (3/5 이하): 재작업 프롬프트 생성

> 💡 **핵심 변경:** 통과 시 바로 다음 오더로 넘어가지 않는다. "검수 → 📝 기록 → 오더" 순서를 반드시 지킨다.

### 검토 등급제 (v2.7 신규) ⭐

> 모든 작업에 같은 강도의 검토를 적용하지 않는다.

| 등급 | 적용 대상 | 검토 내용 | 총괄 부하 |
|------|----------|----------|----------|
| 🟢 **스모크** | 플레이북 내 일반 Task | 빌드 통과 + 작업자 자체 보고 = OK | 최소 |
| 🟡 **전술** | 분리된 위험 오더, 신규 컴포넌트 | 5대 체크 + 핵심 파일 1개 직접 확인 | 보통 |
| 🔴 **전략** | Phase 완료, 마일스톤, 방향 전환 | 전체 방향 + UX 일관성 + 사장님 로컬 확인 | 최대 |

**배치(플레이북) 검토 시:**
1. 플레이북 내 각 Task → 🟢 스모크 (빌드 통과 확인만)
2. 분리 오더 → 🟡 전술 (핵심 파일 직접 확인)
3. Phase 전체 → 🔴 전략 (Phase 경계에서만)

> 💡 **작업자가 기록 위임까지 완료했다면**, 총괄은 기록 검증 + 미결 사항 판단 + 다음 플레이북 생성만 하면 된다.

## STEP 3 — 작업 루프

### 크기별 프로세스 분기 ⭐

모든 작업에 같은 프로세스를 적용하지 않는다.

| 크기 | 기준 | 프로세스 | 세션 수 |
|------|------|---------|---------|
| 🟢 단순 | 1~2줄 수정, 설정값 변경 | 총괄이 직접 수정 | 0 (현재 세션에서 끝) |
| 🟡 보통 | 1~3파일, 명확한 기능 추가 | 오더 생성 → 작업자 | 1 (작업자 세션만) |
| 🔴 복잡 | 4파일+, 신규 페이지, 아키텍처 | _order.md 파일 → 작업자 | 1~2 |
| 🟠 배치 | Phase 단위 다건 작업 | _playbook.md → 작업자 1세션 | 1 (+위험분리 시 추가) |

**단건 모드 (🟡🔴) — 결과 검수는 "다음 총괄 세션"에서 합친다:**
```
[총괄 세션 A] 오더 생성
  → [작업자 세션] 실행
[총괄 세션 B] 세션A 결과 검수 + 세션B 오더 생성 (2 in 1)
  → [작업자 세션] 실행
[총괄 세션 C] ...반복
```

**배치 모드 (🟠) — 플레이북으로 왕복 최소화:** ⭐
```
[총괄 세션 A] Phase 분석 → _playbook.md 생성 (+ 위험 분리건은 다음 _order.md 슬롯으로 예약)
  → [작업자 세션 1] _playbook.md 순서대로 전부 실행 (체크포인트 자체 확인)
  → [작업자 세션 2] _order.md 실행 (위험 분리건, 있을 때만)
[총괄 세션 B] 일괄 검토 (검토 등급제 적용) + 다음 Phase 플레이북 생성
```
> 💡 **대부분의 Phase는 배치 모드로 처리.** 총괄 세션 2번 + 작업자 1~2번 = 총 3~4번 세션으로 Phase 완료.

### 일반 루프 (강제 체크리스트) ⭐

> ⚠️ **절대 규칙:** 아래 순서를 건너뛰지 않는다. 특히 [2]를 빼먹는 일이 절대 없어야 한다.
> 검수 결과가 좋으면 흥분해서 바로 다음 오더로 넘어가고 싶지만, **업데이트 없이 오더 없다.**

```
[1] 🔍 검수 — 이전 결과 검수 (있으면) → 5대 체크 + 직접 코드 확인
    ⬇️ (통과 시에만 [2]로)
[2] 📝 기록 업데이트 — 반드시 실행! 건너뛰기 금지!
    ├── _context.md: "최근 완료"에 추가
    ├── _context.md: "핵심 결정" 추가 (있으면)
    ├── DECISION_LOG.md: 장기 영향 결정이면 날짜/이유/영향/재검토 조건 기록
    ├── _context.md: "다음 할 일" 업데이트
    ├── PROJECT_TASKS.md: 해당 태스크 [x] 체크 + 마일스톤 기록
    └── ✅ 업데이트 완료 확인 메시지 출력
    ⬇️
[3] 🚦 중간 검증 게이트 — Phase 경계인가? (아래 규칙 참조)
    ⬇️
[4] 🤝 협의 — 사용자와 다음 작업 결정
[5] 📋 오더 생성 — 크기에 따라 방식 결정
[6] 🔚 세션 종료 체크 — 10회 이상이면 마무리 권유
```

> 💡 **기억법:** "검수 → 기록 → 오더" — 이 3단계가 총괄의 심장박동이다.

### 중간 검증 게이트 (Phase 완료 시) 🚦

> Phase 경계(Phase 0→1, 1→2, 2→3 등)에 도달하면 **반드시** 사장님에게 확인을 요청한다.
> 확인 전까지 다음 Phase의 오더를 발행하지 않는다.

```
🔍 [Phase명] 개발이 완료되었습니다!
로컬에서 아래 시나리오를 직접 확인해 주세요:

1. [핵심 동작 1] — 예: /admin 접속 → 로그인 성공
2. [핵심 동작 2] — 예: 컬렉션 클릭 → 컬러 목록 표시
3. [핵심 동작 3] — 예: 컬러 추가 → 저장 → 목록 반영

확인 후 '통과' 또는 발견한 문제를 알려주세요.
⚠️ 확인 전까지 다음 Phase 오더를 발행하지 않습니다.
```

### 긴급 루프 ("긴급 수정" 트리거)
```
[1] 증상 파악 → 에러 메시지 / 문제 상황
[2] 바로 오더 생성 → 디버깅 프롬프트
[3] 사후에 _context.md + PROJECT_TASKS.md 기록 (건너뛰지 않음)
```
