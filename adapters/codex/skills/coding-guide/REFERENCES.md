# 코딩가이드 REFERENCES

> 긴 에스컬레이션 양식과 상태 표기는 이 파일에 둔다. 실행 흐름은 `SKILL.md`를 따른다.

## 에스컬레이션 프로토콜 상세

코딩가이드는 STEP 1 작업 해석 후 아래 상황을 감지하면 코딩을 시작하지 않고 에스컬레이션한다.

| # | 상황 | 감지 기준 | 에스컬레이션 유형 |
|---|------|----------|-----------------|
| 1 | 오더 모호 | 대상 파일, 완료 기준, 또는 금지 영역이 특정 불가 | 🟡 반려 → 명확화 요청 |
| 2 | 완료 기준 불가 | 기술적으로 달성 불가능하거나 현재 환경에서 검증 불가 | 🔴 반려 → 대안 제시 |
| 3 | 범위 초과 | 오더 1개로 안전하게 처리 불가 | 🟡 분할 제안 |
| 4 | 실행 중 난관 | 코딩 시작 후 예상 못한 의존성/충돌 발견 | 🟡 부분 완료 보고 |

### 유형 1: 오더 모호

감지 기준:
- 대상 파일이 "관련 파일 수정"처럼 추상적이다.
- 완료 기준이 "잘 되게"처럼 주관적이다.
- 금지 영역이 없거나 "알아서"로 되어 있다.
- 참고 파일이 실제로 존재하지 않는다.

보고 양식:

```text
⚠️ 오더 명확화 요청
━━━━━━━━━━━━
오더 #NNN의 아래 항목이 실행하기에 모호합니다.

모호한 항목:
1. [항목] — [왜 모호한지 한 줄]
2. [항목] — [왜 모호한지 한 줄]

필요한 정보:
- [구체적으로 뭘 알아야 하는지]

💡 총괄 시작으로 오더를 재발행하거나, 여기서 바로 답해주세요.
━━━━━━━━━━━━
```

추측 실행은 금지한다. "아마 이런 뜻이겠지"로 진행하지 않는다.

### 유형 2: 완료 기준 불가

감지 기준:
- 요청된 라이브러리/API가 현재 환경에 없고 설치 권한이 불명확하다.
- 요청된 동작이 프레임워크 제약과 충돌한다.
- 완료 기준이 현재 데이터/상태로는 검증 불가하다.

보고 양식:

```text
🔴 오더 실행 불가 보고
━━━━━━━━━━━━
오더 #NNN의 완료 기준을 현재 환경에서 달성할 수 없습니다.

불가 사유:
- [기술적 이유 — 구체적 파일/환경/제약 인용]

대안 제시:
- A안: [대안 1 — 트레이드오프 한 줄]
- B안: [대안 2 — 트레이드오프 한 줄]

💡 총괄 시작으로 대안을 선택하거나 오더를 재발행해주세요.
━━━━━━━━━━━━
```

대안은 방향만 제시한다. 사용자가 선택하기 전에는 대안 코드를 직접 구현하지 않는다.

### 유형 3: 범위 초과

감지 기준:
- 수정 대상 파일이 5개를 넘는다.
- 복수의 독립 기능이 1개 오더에 혼합되어 있다.
- 예상 작업 시간이 오더 추천 시간의 2배를 넘는다.
- 파일 간 의존성이 순차 처리를 요구한다.

보고 양식:

```text
⚠️ 오더 분할 제안
━━━━━━━━━━━━
오더 #NNN이 안전하게 처리하기에 범위가 큽니다.

분할 제안:
- Task A: [무엇 — 영향 파일 N개]
- Task B: [무엇 — 영향 파일 N개] [의존: Task A 후]
- Task C: [무엇 — 영향 파일 N개] [독립]

이유: [왜 분할이 안전한지 한 줄]

💡 동의하시면 Task A부터 진행합니다.
    또는 총괄 시작으로 플레이북을 생성해주세요.
━━━━━━━━━━━━
```

분할 제안에는 반드시 `[독립]` 또는 `[의존: Task A 후]`를 표시한다.

### 유형 4: 실행 중 난관

감지 기준:
- 예상 못한 의존성이 발견되어 오더 범위 밖 파일 수정이 필요하다.
- 기존 코드의 결함이 오더 결과를 막는다.
- 빌드 에러를 3회 시도 후에도 해결하지 못했다.

보고 양식:

```text
⚠️ 부분 완료 보고
━━━━━━━━━━━━
오더 #NNN — 일부 완료, 나머지 진행 불가.

완료된 부분:
- [뭘 했는지]

미완료 부분:
- [뭘 못 했는지]

난관:
- [왜 못 했는지 — 구체적 파일/에러/의존성]

제안:
- [다음 오더에서 어떻게 처리할지]

━━━ 수정 파일 (완료분) ━━━
- `[경로]` — [변경 내용]
━━━━━━━━━━━━
```

`_order.md`의 "작업 결과" 섹션에도 부분 완료 상태를 기록한다.

## 에스컬레이션 판단 플로우

```text
STEP 1 작업 해석 완료
    ↓
모호한 항목 있나? ──YES──→ 유형 1: 반려 + 명확화 요청 → STOP
    ↓ NO
완료 기준 달성 가능? ──NO──→ 유형 2: 반려 + 대안 제시 → STOP
    ↓ YES
안전 범위 내? ──NO──→ 유형 3: 분할 제안 → 승인 후 진행
    ↓ YES
STEP 2로 진행
    ↓
예상 못한 난관? ──YES──→ 유형 4: 부분 완료 보고 → STOP
    ↓ NO
STEP 4~5 자체 검증 + 결과 보고
```

## 총괄매니저 검수 상태 연동

총괄매니저가 `_order.md`의 "작업 결과"를 읽을 때 아래 상태를 해석한다.

| 상태 | 의미 | 총괄 행동 |
|------|------|----------|
| ✅ 완료 | 정상 완료 | 결과 검수 → 기록 업데이트 → 다음 오더 |
| ⚠️ 부분 완료 | 유형 4 | 완료분 검수 + 미완료분 새 오더 |
| 🟡 반려 | 유형 1 또는 3 | 오더 재발행 또는 플레이북 변환 |
| 🔴 불가 | 유형 2 | 대안 검토 → 새 오더 |
