# 암행어사 REFERENCES

> 모드별 상세 절차, 공격 질문, 보고서 템플릿은 이 파일에 둔다. 실행 라우터와 Hard Fail은 `SKILL.md`, 최종 검수는 `CHECKLIST.md`를 따른다.

## 모드별 상세 절차

### Mode A: 전수 스캔

프로젝트 파일이 존재할 때 사용한다. 사용자에게 파일 목록을 묻지 말고 직접 스캔한다.

스캔 대상:

1. `_context.md`: 현재 상태와 결정 사항
2. `_order.md`: 현재 작업 지시와 결과
3. `_archive.md`: 과거 기록
4. `*PRD*.md`: 기획 문서
5. `*DESIGN_SYSTEM*.md`: 디자인 문서
6. `PROJECT_BRIEF.md`: 오피스아워 결과
7. `package.json`: 의존성, 스크립트, 프레임워크
8. `src/` 또는 `app/`: 코드 구조
9. 핵심 소스 파일: 최소 10개 직접 열람
10. `SKILL.md`: 스킬 시스템 자체가 대상이면 필수 열람

공격 벡터:

| # | 벡터 | 질문 | 위생 진단 |
|---|------|------|-----------|
| 1 | 모순 | 문서끼리, 코드와 문서 사이에 모순이 있는가? | PRD/디자인시스템 사양과 실제 구현 불일치 |
| 2 | 누락 | 있어야 하는데 없는 기능, 예외 처리, 검증이 있는가? | 빈 `catch`, 빠진 실패 처리 |
| 3 | 과잉 | 불필요하게 복잡하거나 안 쓰는 코드가 있는가? | 미사용 파일, 데드 코드, 불필요한 의존성 |
| 4 | 취약점 | 깨지기 쉬운 하드코딩, 단일 장애점, 보안 허점이 있는가? | 하드코딩 색상/간격/API 키/개인 경로 |
| 5 | 확장성 | 사용자나 데이터가 10배 늘면 무너지는가? | 비효율 루프, 고정 데이터 구조 |
| 6 | 사용자 경험 | 실제 사용자가 혼란스러워할 부분이 있는가? | 일관성 없는 피드백, 모호한 에러 안내 |
| 7 | 방향성 | 현재 코드가 프로젝트 목표나 피벗 이력과 어긋나는가? | 남아 있는 레거시 기능/문서 |

### Mode B: 아이디어 검증

프로젝트 파일이 없고 텍스트/아이디어/브리프만 있을 때 사용한다.
`PROJECT_BRIEF.md`가 있으면 함께 읽는다.

7대 공격 질문:

| # | 벡터 | 질문 |
|---|------|------|
| 1 | 시장 맹점 | 이 아이디어가 실패할 가장 큰 이유는? 시장에 이미 있지 않은가? |
| 2 | 타겟 회의 | 타겟 사용자가 실제로 안 쓸 이유는? 돈을 낼 만큼 절실한가? |
| 3 | 대안 충분 | 기존 대안으로 충분히 해결되지 않는가? |
| 4 | 기술 과소평가 | 과소평가한 기술 난이도나 숨은 복잡성은? |
| 5 | 비즈니스 약점 | 수익 구조와 성장 경로의 약점은? |
| 6 | 팀/실행 역량 | 실행할 사람과 시간, 역량이 충분한가? |
| 7 | 타이밍/외부 환경 | 지금이 적기인가? 규제, 경쟁, 트렌드가 불리하지 않은가? |

각 질문은 공격하되, 반론 가능성을 한 줄로 함께 남긴다.

### Mode C: 전문가 렌즈

전문가 관점, 숲 밖 관점, 구조적 평가 요청에 사용한다.
Mode A가 있는 것의 결함을 찾는다면, Mode C는 없는 구조의 공백을 찾는다.

전문가 선택:

```text
어떤 전문가의 눈으로 볼까요?
1. 코딩 프로: 기술 아키텍처, 코드 품질, 개발 프로세스
2. UX/UI 전문가: 사용자 경험, 인터페이스, 접근성
3. 사업가/PM: 시장성, 수익 구조, 성장 전략
4. 보안 전문가: 취약점, 인증, 데이터 보호
5. 시스템 아키텍트: 확장성, 의존성, 인프라
6. 직접 입력
```

사용자가 "전부 다"라고 하면 1~5를 순회한다.

3단계 분석:

1. 기대 기준 수립: 해당 전문가라면 당연히 기대하는 기준을 먼저 쓴다.
2. 현실 대조: 기대 기준과 실제 프로젝트를 항목별로 비교한다.
3. 성숙도 판정: 10개 내외 카테고리를 5단계 레벨로 평가한다.

성숙도 레벨:

| 레벨 | 의미 | 기준 |
|------|------|------|
| Lv.1 부재 | 해당 영역이 없거나 심각하게 미달 | 근본 결함 |
| Lv.2 초급 | 있지만 기본 수준 | 최소 충족 |
| Lv.3 중급 | 대부분 충족, 일부 개선 필요 | 평균 수준 |
| Lv.4 고급 | 전문가 기대치 대부분 충족 | 우수 |
| Lv.5 전문가 | 업계 모범 사례 수준 | 최상급 |

Lv.4 이상은 정말 강한 경우에만 준다. 인플레이션 금지.

Mode C는 출시점검이 아니다. 배포 가능 여부는 `출시점검`으로 따로 판단한다.

### Mode D: Skilltree Audit

스킬트리 자체를 제품처럼 감사한다.
기준 원본은 GitHub repo의 `source/` 디렉터리다.
`adapters/`와 로컬 설치본은 생성물 또는 설치본이므로 drift 비교 대상으로만 본다.

스캔 대상:

1. `CORE_PRINCIPLES.md`: 원칙, 문서 우선순위, 품질 기준
2. `SKILL_INDEX.md`: 라우터, 버전, 스킬 목록, 변경 이력
3. 모든 `*/SKILL.md`: frontmatter, 트리거, 출력 기준, 금지사항
4. `REFERENCES.md`, `CHECKLIST.md`, `templates/`, `scripts/`: 참조 무결성
5. adapter 결과물: 생성물 drift 여부

9대 공격 벡터:

| # | 벡터 | 질문 | Hard Fail 예시 |
|---|------|------|----------------|
| 1 | Canonical | 기준 원본이 명확한가? | 복제본을 기준으로 판단 |
| 2 | Router | 요청이 어떤 스킬로 가야 하는지 명확한가? | `SKILL_INDEX.md` 라우팅 누락 |
| 3 | Version | YAML, 제목, catalog, index 버전이 일치하는가? | v2.0과 v1.4 혼재 |
| 4 | Trigger | description과 실행 트리거가 발견 가능한가? | 트리거가 본문에만 있음 |
| 5 | Output | 최소 출력 기준과 완료 기준이 있는가? | 산출물이 모호함 |
| 6 | Conflict | 출력/저장 규칙이 충돌하지 않는가? | 통합 1파일과 분리 저장 동시 지시 |
| 7 | Reference | 참조 파일이 실제 존재하는가? | 없는 템플릿 경로 참조 |
| 8 | Size | 큰 스킬이 분리 기준을 검토했는가? | 긴 예시가 `SKILL.md`에 누적 |
| 9 | Adapter | Codex/Antigravity/Claude가 다르게 해석할 표현이 있는가? | 특정 환경 tool 이름에 고정 |

## 보고서 템플릿

### Mode A/B: 감찰 보고서

```markdown
# 암행어사 감찰 보고서

- 감찰일: YYYY-MM-DD
- 대상: [프로젝트명 또는 입력]
- 모드: Mode A 전수 스캔 / Mode B 아이디어 검증
- 스캔 범위: [직접 확인한 파일/입력]

## 발견된 문제

### 심각
1. [문제] - [근거: 파일명:라인]
   - 영향:
   - 제안:

### 경고
1. [문제] - [근거]
   - 영향:
   - 제안:

### 참고
1. [문제] - [근거]
   - 제안:

## 위생 점검 리스트

- [ ] **가비지 파일:** [경로] ([이유])
- [ ] **문서 불일치:** [경로] ([불일치 내용])
- [ ] **하드코딩 지양:** [경로:라인] ([치환 방향])

## 요약

- 심각: N건
- 경고: N건
- 참고: N건
- 위생 대상: N건
```

저장 위치:

- 기본: 프로젝트 루트 `_audit_YYYY-MM-DD.md`
- 같은 날 재감찰: `_audit_YYYY-MM-DD_2.md`

### Mode C: 전문가 렌즈 보고서

```markdown
# 전문가 렌즈 평가 보고서

- 평가일: YYYY-MM-DD
- 전문가 유형: [선택된 유형]
- 대상: [프로젝트/시스템명]
- 성숙도: Lv.X [레벨명]

이 레벨은 전문가 관점의 성숙도 진단이다. 배포 판정은 `출시점검`을 사용한다.

## 성숙도 레이더

| # | 항목 | 레벨 | 비고 |
|---|------|------|------|
| 1 | ... | Lv.X | ... |

## 최대 강점

[1~2개만. 칭찬이 아니라 구조 판단 근거로 쓴다.]

## 최대 약점

[1~2개]

## 빠진 것

1. [빠진 구조] - [왜 있어야 하는지]

## 돌파 과제

1. [가장 임팩트 큰 개선] - [예상 효과]

## 한 줄 평가

[솔직한 한 줄]
```

## 사용 시나리오

### 오피스아워 후

`PROJECT_BRIEF.md`가 생성되면 "암행어사, PROJECT_BRIEF 검증해줘"로 Mode B를 실행한다.
브리프의 약점과 반론 가능성을 찾고, 오피스아워로 돌아가 보완한다.

### PRD 완성 후

PRD 작성 후 "암행어사"를 실행한다.
PRD의 모순, 누락, 과잉, 인수 조건 약점을 찾는다.

### 프로젝트 중간

방향이 찜찜할 때 Mode A를 실행한다.
`_context.md`, `_order.md`, 코드, 문서를 함께 읽고 감찰 보고서를 남긴다.

### 전문가 렌즈

일반 감찰을 여러 번 돌려 문제가 포화됐을 때 사용한다.
기술, UX, PM, 보안, 아키텍처 관점에서 없는 구조를 찾는다.

### 스킬트리 감사

전역 스킬을 여러 번 수정했거나 adapter drift가 의심될 때 사용한다.
CORE, INDEX, catalog, 모든 SKILL, support files, adapter 결과물을 비교한다.

## 경계 규칙

- Mode A/B/D는 문제 탐색이 중심이다. Mode C만 성숙도와 빠진 구조를 평가한다.
- Mode C는 GO/NO-GO를 내리지 않는다.
- Mode D는 일반 코드리뷰가 아니다.
- 감찰 보고서는 짧고 날카롭게 쓴다. 문제당 2줄 이내를 기본으로 한다.
- 근거가 없으면 발견 항목으로 올리지 않는다.
