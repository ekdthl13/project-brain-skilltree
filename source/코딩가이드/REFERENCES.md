# 코딩가이드 REFERENCES

> 상세 양식, 예시, 조건부 프로토콜은 이 파일에 둔다. 실행 루프와 Hard Fail은 `SKILL.md`, 최종 검수는 `CHECKLIST.md`를 따른다.

## 환경 스캔 상세

코딩 시작 전 프로젝트 파일을 자동으로 읽는다. 사용자에게 "어떤 프레임워크인가요?"처럼 물어보지 않는다.

### 필수 스캔

| 스캔 대상 | 파악 내용 |
|-----------|-----------|
| `AGENTS.md` | 프로젝트 루트에 존재하면 반드시 준수 |
| `_order.md` | 작업 목표, 대상 파일, 금지 영역, 완료 기준 |
| `_context.md` | 존재할 때 현재 상태와 핵심 결정 |
| `package.json` | 기술 스택, 의존성, 스크립트 |
| `src/` 또는 `app/` | 폴더 패턴과 기존 컴포넌트 구조 |

### 프레임워크 환경 검증

훈련 데이터가 현재 프로젝트 버전과 다를 수 있으므로 버전 민감 작업에서는 현재 환경을 확인한다.

```text
[ ] AGENTS.md 읽기
[ ] package.json에서 주요 프레임워크 버전 확인
[ ] 프로젝트 안의 공식 문서/기존 패턴 확인
[ ] 확인한 버전과 주의사항을 작업 결과 상단에 기록
```

예:

```text
환경 확인:
- Next.js v16.2.4: params는 Promise, await 필수
- AGENTS.md 확인: node_modules/next/dist/docs/ 참조 지시 준수
```

```text
대상 파일: [수정/생성할 파일 목록]

금지 영역: [건드리면 안 되는 것]

```

`_order.md`가 있는 경우 이 해석을 보여주되 응답을 기다리지 않고 진행한다. 단, 에스컬레이션 조건이면 중단한다.

## 에스컬레이션 프로토콜 상세

코딩가이드는 STEP 1 작업 해석 후 아래 상황을 감지하면 코딩을 시작하지 않고 에스컬레이션한다.

| # | 상황 | 감지 기준 | 에스컬레이션 유형 |
|---|------|----------|-----------------|
| 1 | 오더 모호 | 대상 파일, 완료 기준, 또는 금지 영역이 특정 불가 | 🟡 반려 → 명확화 요청 |
| 2 | 완료 기준 불가 | 기술적으로 달성 불가능하거나 현재 환경에서 검증 불가 | 🔴 불가 → 대안 제시 |
| 3 | 범위 초과 | 오더 1개로 안전하게 처리 불가 | 🟡 분할 제안 |
| 4 | 실행 중 난관 | 코딩 시작 후 예상 못한 의존성/충돌 발견 | ⚠️ 부분 완료 보고 |

### 유형 1: 오더 모호

감지 기준:
- 대상 파일이 "관련 파일 수정"처럼 추상적이다.
- 완료 기준이 "잘 되게"처럼 주관적이다.
- 금지 영역이 없거나 "알아서"로 되어 있다.
- 참고 파일이 실제로 존재하지 않는다.

보고 양식:

```text
🟡 오더 명확화 요청
━━━━━━━━━━━━
오더 #NNN의 아래 항목이 실행하기에 모호합니다.

모호한 항목:
1. [항목] — [왜 모호한지 한 줄]
2. [항목] — [왜 모호한지 한 줄]

필요한 정보:
- [구체적으로 뭘 알아야 하는지]

총괄 시작으로 오더를 재발행하거나, 여기서 바로 답해주세요.
━━━━━━━━━━━━
```

### 유형 2: 완료 기준 불가

감지 기준:
- 요청된 라이브러리/API가 현재 환경에 없고 설치 권한이 불명확하다.
- 요청된 동작이 프레임워크 제약과 충돌한다.
- 완료 기준이 현재 데이터/상태로는 검증 불가하다.

보고 양식:

```text
🔴 오더 실행 불가 보고
━━━━━━━━━━━━
오더 #NNN의 완료 기준을 현재 환경에서 달성할 수 없습니다.

불가 사유:
- [기술적 이유 — 구체적 파일/환경/제약 인용]

대안:
- A안: [대안 1 — 트레이드오프 한 줄]
- B안: [대안 2 — 트레이드오프 한 줄]
━━━━━━━━━━━━
```

대안은 방향만 제시한다. 사용자가 선택하기 전에는 대안 코드를 직접 구현하지 않는다.

### 유형 3: 범위 초과

감지 기준:
- 수정 대상 파일이 5개를 넘는다.
- 복수의 독립 기능이 1개 오더에 혼합되어 있다.
- 예상 작업 시간이 오더 추천 시간의 2배를 넘는다.
- 파일 간 의존성이 순차 처리를 요구한다.

보고 양식:

```text
🟡 오더 분할 제안
━━━━━━━━━━━━
오더 #NNN이 안전하게 처리하기에 범위가 큽니다.

분할 제안:
- Task A: [무엇 — 영향 파일 N개]
- Task B: [무엇 — 영향 파일 N개] [의존: Task A 후]
- Task C: [무엇 — 영향 파일 N개] [독립]

이유: [왜 분할이 안전한지 한 줄]
━━━━━━━━━━━━
```

분할 제안에는 반드시 `[독립]` 또는 `[의존: Task A 후]`를 표시한다.

### 유형 4: 실행 중 난관

감지 기준:
- 예상 못한 의존성이 발견되어 오더 범위 밖 파일 수정이 필요하다.
- 기존 코드의 결함이 오더 결과를 막는다.
- 빌드 에러를 3회 시도 후에도 해결하지 못했다.

보고 양식:

```text
⚠️ 부분 완료 보고
━━━━━━━━━━━━
오더 #NNN — 일부 완료, 나머지 진행 불가.

완료된 부분:
- [뭘 했는지]

미완료 부분:
- [뭘 못 했는지]

난관:
- [왜 못 했는지 — 구체적 파일/에러/의존성]

제안:
- [다음 오더에서 어떻게 처리할지]

━━━ 수정 파일 (완료분) ━━━
- `[경로]` — [변경 내용]
━━━━━━━━━━━━
```

`_order.md`의 "작업 결과" 섹션에도 부분 완료 상태를 기록한다.

## 테스트 작성 규칙

무조건적인 테스트 작성이 아니라, 리스크에 따라 적용한다.

| 중요도 | 대상 코드 | 테스트 요구 |
|--------|-----------|-------------|
| 🔴 필수 | 핵심 비즈니스 로직, 상태 관리, 계산/파싱 유틸 | 구현 전 실패 테스트 또는 동등한 검증 먼저 |
| 🟡 권장 | API route, 복잡한 폼, 사용자 입력 흐름 | 구현 후 해피/언해피 패스 |
| 🟢 면제 가능 | 단순 마크업, 정적 페이지, 단순 스타일 | 빌드/렌더 확인 |

테스트 프레임워크가 없으면 임의로 패키지를 설치하지 않는다. 대신 수동 검증 시나리오와 실행 결과를 작업 결과에 남긴다.

## 코드 출력 금지 패턴

전체 구현을 요구받았을 때 아래 형태는 금지한다.

```text
// ...
// rest of code
// implement here
// TODO
/* ... */
// similar to above
// continue pattern
// add more as needed
// 나머지도 비슷합니다
// 나머지 생략
```

응답에서도 "이하 생략", "나머지도 같은 패턴"처럼 중간을 건너뛰지 않는다.

토큰 한계 접근 시에는 품질을 낮추지 말고 깔끔한 중단점에서 멈춘다.

```text
[PAUSED — X/Y 완료. "continue"로 재개]
```

## 디자인 토큰 예시

`DESIGN_SYSTEM.md`가 존재하면 토큰을 사용한다.

```css
/* 금지 */
color: #3B82F6;
padding: 12px;
font-size: 14px;
border-radius: 8px;

/* 권장 */
color: var(--color-primary);
padding: var(--spacing-3);
font-size: var(--font-size-sm);
border-radius: var(--radius-md);
```

Tailwind 프로젝트:

```tsx
// 금지
className="text-[#3B82F6] p-[12px]"

// 권장
className="text-primary p-3"
```

## 오류 처리 예시

프론트엔드:

```typescript
try {
  const data = await fetchData();
  return data;
} catch (error) {
  showToast("데이터를 불러오지 못했습니다.");
  console.error("[fetchData]", error);
  return [];
}
```

API / 서버:

```typescript
{ success: true, data: {...} }
{ success: false, error: { code: "NOT_FOUND", message: "..." } }
```

금지:

```typescript
try { ... } catch (e) {}
try { ... } catch (e) { return null; }
catch (e) { alert(e.message); }
```

## 디버깅 4단계 프로토콜

복잡한 버그, 런타임 크래시, 논리 에러는 아래 순서로 보고한다.

1. **가설 수립:** 에러 트레이스와 로그에서 의심 포인트 1~2개를 세운다.
2. **격리 테스트:** 의심 코드만 따로 재현하거나 최소 스크립트로 좁힌다.
3. **수정:** 가설에 맞는 최소 변경을 한다.
4. **전파 방지:** 유사 패턴을 검색하고 필요한 범위만 함께 조치한다.

## 안전한 리소스 청소 프로토콜

위생 정리 오더 또는 미사용 파일 청소 시:

1. 삭제 전 전체 검색으로 실제 미참조인지 확인한다.
2. 하드코딩 값을 제거할 때 `DESIGN_SYSTEM.md`의 공식 토큰과 대조한다.
3. 토큰이 없으면 임의 선언하지 말고 총괄/디자인시스템에 피드백한다.
4. 사양이나 아키텍처 규칙이 바뀌면 관련 문서를 함께 맞춘다.

## Git 최소 컨벤션

Git이 설정된 프로젝트에서, 사용자가 커밋을 요청하거나 프로젝트 관례가 명확할 때만 적용한다.

```text
[타입] 변경 내용 한 줄 요약

feat     — 새 기능
fix      — 버그 수정
style    — 스타일/CSS 변경
refactor — 리팩토링
docs     — 문서 변경
chore    — 설정, 의존성 변경
```

- 1 오더 = 1 논리 변경이 기본이다.
- 관련 없는 사용자 변경은 되돌리지 않는다.
- 커밋 전에는 검증과 변경 범위를 확인한다.

## 컴포넌트 작성 참고

React/Next.js 예시는 기본값일 뿐이다. 기존 프로젝트의 패턴이 항상 우선한다.

```text
ComponentName/
├── ComponentName.tsx
├── ComponentName.module.css
└── index.ts
```

컴포넌트 작성 순서:

1. import
2. type/interface
3. 상태와 훅
4. handler
5. render

다른 프레임워크 프로젝트에서는 해당 프레임워크의 관례를 따른다.

## 총괄매니저 검수 상태 연동

| 상태 | 의미 | 총괄 행동 |
|------|------|----------|
| ✅ 완료 | 정상 완료 | 결과 검수 → 기록 업데이트 → 다음 오더 |
| ⚠️ 부분 완료 | 유형 4 | 완료분 검수 + 미완료분 새 오더 |
| 🟡 반려 | 유형 1 또는 3 | 오더 재발행 또는 플레이북 변환 |
| 🔴 불가 | 유형 2 | 대안 검토 → 새 오더 |
